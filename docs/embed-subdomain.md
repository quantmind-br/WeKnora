# Embed Standalone Subdomain Deployment (Optional)

> **One-liner**: Put the chat page on its own `embed.example.com`, separate from the main site `app.example.com`. **Most deployments don't need this step** — the main site and embed working on the same origin is fine. Only consider this when you have a clear requirement for security isolation.

## First, clarify the three "sites"

When embedding chat, three types of addresses are actually involved (they can be the same, or different):

| Role | Example | Purpose |
|------|---------|---------|
| **A. Business site (host)** | `https://shop.example.com` | Your storefront / docs site; this is where you paste the Widget script or iframe |
| **B. Embed page origin** | `https://app.example.com` or `https://embed.example.com` | Serves `embed.html`, `weknora-widget.js`; the chat iframe loads from here |
| **C. WeKnora API** | Usually the same origin as B, e.g. `https://app.example.com/api` | Backend interface |

**Default (recommended for getting started)**: B and the main admin backend are both on `https://app.example.com`, and A can be any third-party domain.

```
shop.example.com          app.example.com
┌─────────────────┐       ┌──────────────────────────┐
│ <script src=    │       │ /weknora-widget.js       │
│  app.../widget> │──────►│ /embed/:channelId        │
│                 │       │ /api/v1/embed/...        │
│  (floating iframe) │◄──────│                          │
└─────────────────┘       └──────────────────────────┘
```

**Standalone subdomain (advanced)**: Split B out to `https://embed.example.com`, leaving the main site `https://app.example.com` with only the admin backend.

```
shop.example.com          embed.example.com        app.example.com
┌─────────────────┐       ┌──────────────────┐     ┌─────────────┐
│ Widget script    │──────►│ embed static page +API │     │ Admin backend │
│ iframe points to embed │◄──────│ (no index SPA)    │     │ (optionally split) │
└─────────────────┘       └──────────────────┘     └─────────────┘
```

## When do you need a standalone subdomain?

| Scenario | Needed? |
|------|----------|
| Internal testing, PoC, single-origin Docker deployment | **Not needed** |
| Main site has `X-Frame-Options: SAMEORIGIN`, but you want to embed chat into a third-party page | **Not needed** (what's being embedded is the `/embed/*` page, not the admin SPA) |
| You want the embed site to not carry the main site's login cookies, to reduce exposure | **Worth considering** |
| You want the CDN / WAF to rate-limit / cache embed traffic separately | **Worth considering** |
| Compliance requires "external embedding" and "internal admin" to be on different origins | **Needed** |

Local development: `http://localhost:5173` works fine on a single origin — Vite already routes `/embed/*` to `embed.html`, **no need** to configure a subdomain.

## How to configure

### 1. Tell the admin panel the "embed page's public address"

When the admin panel generates iframe / Widget code, it needs to know B's address. Set this in `frontend/public/config.js` (or the config generated by the Docker startup script):

```javascript
window.__RUNTIME_CONFIG__ = {
  // Origin for the embed page and widget.js; leave empty to use the current browser's domain
  EMBED_BASE_URL: 'https://embed.example.com',
  MAX_FILE_SIZE_MB: 50,
};
```

This can also be injected at build time via an environment variable: `VITE_EMBED_BASE_URL=https://embed.example.com` (optional).

### 2. Nginx: a separate server block that serves only the embed

There's a commented-out example at the top of `frontend/nginx.conf`. Key points:

- `server_name embed.example.com`
- Only expose: `/embed/*` → `embed.html`, `/weknora-widget.js`, `/assets/*`
- Proxy `/api/` to the WeKnora backend (the same backend as the main site works fine)
- **Do not** mount the full `index.html` admin SPA on this server (to reduce attack surface)

The main site's `server` block can keep `X-Frame-Options: SAMEORIGIN` — this doesn't affect third-party sites embedding the embed subdomain's iframe.

### 3. What goes in the domain whitelist?

The channel's "domain whitelist" validates the **`Origin` header of API requests**, not an abstract "which sites are allowed to paste the script" concept.

What you actually need to fill in:

1. **Embed page origin** (required) — this is the Origin the browser sends when the chat iframe makes API calls
   - Same-origin deployment: `https://app.example.com`
   - Standalone subdomain: `https://embed.example.com`
2. **Your business backend's origin** (recommended when using secure mode) — when your own "token exchange endpoint" calls `POST .../exchange` server-side, it needs to send an `Origin` header matching the whitelist (see [embed-secure-mode.md](./embed-secure-mode.md))

The third-party storefront `https://shop.example.com` **usually does not** need to be in the whitelist (it only loads the script — it doesn't call the embed API directly).
Only if you proxy the embed under the storefront's own domain path (uncommon) would you need to add the storefront's domain.

## Widget cross-origin and sandbox

When the host site A and the embed origin B are **on different origins**, `weknora-widget.js` automatically adds `sandbox` to the inner iframe (you can also set this manually with `data-sandbox="true"`).

When A and B share the same origin, just keep the default — no need for `data-sandbox`.

## Checklist

- [ ] `EMBED_BASE_URL` matches the actual access address (including `https`)
- [ ] The embed subdomain can open `/embed/<channelId>` and `/weknora-widget.js`
- [ ] The embed subdomain's `/api/` can reach the backend
- [ ] The channel whitelist includes the embed origin (and the business backend origin, in secure mode)
- [ ] The URL in the snippet copied from the admin panel has been updated to the embed subdomain
