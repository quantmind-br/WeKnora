# Shared Space Documentation

This document describes the **Shared Space** feature in WeKnora, including space creation and joining, member roles and permissions, knowledge base and agent sharing rules, the agent deactivation mechanism, and how a user's final access permission to a knowledge base is calculated.

> Shared Spaces solve "cross-space collaboration" and are orthogonal to the role permissions within a single space ([Space RBAC Documentation](./RBAC说明.md)): a cross-space write operation must pass through both gates simultaneously. See the "Relationship with Shared Spaces" section in the RBAC documentation for details.

---

## 1. Shared Space Overview

### 1.1 What Is a Shared Space

A shared space is the vehicle for cross-space collaboration. Users can belong to different spaces (accounts) within the same system, and by **joining the same shared space**, they can achieve:

- Sharing knowledge bases: sharing a knowledge base from your own space to the shared space, for use by other members of the space;
- Sharing agents: sharing an agent from your own space to the shared space, for use by other members in scenarios such as conversations;
- Accessing knowledge bases shared by others: seeing and opening, in the "Knowledge Base List," knowledge bases shared with you via the shared space;
- Selecting and using these shared knowledge bases and shared agents in scenarios such as conversations and agents.

The data and permission relationships are briefly as follows:

- **Space**: the ownership unit for knowledge bases and agents — each knowledge base/agent belongs to one space;
- **Shared Space**: does not own knowledge bases or agents; it only records "a certain knowledge base/agent has been shared to a certain space" and "the permission at the time of sharing";
- **Member**: a user who joins a space via an invite code or admin invitation, holding one role within the space (admin / editor / viewer).

### 1.2 Core Concept Comparison

| Concept | Description |
|------|------|
| Shared Space | The "Organization" in the system, used for sharing knowledge bases and agents across spaces |
| Space Creator | The user who created the space; automatically becomes the admin of that space, and cannot be removed or demoted |
| Space Member | A user who joined via an invite code or was invited by an admin, holding one of the roles: admin, editor, or viewer |
| Knowledge Base/Agent Ownership | A knowledge base or agent always belongs to one space; sharing it to a shared space does not change ownership — it only establishes a "space ↔ knowledge base/agent" sharing relationship |
| Sharing Relationship | A record indicating: a certain knowledge base has been shared to a certain shared space with a certain permission (read-only/writable); or a certain agent has been shared to a certain shared space in read-only mode |

## 2. Creating, Joining, and Leaving a Shared Space

### 2.1 Creating a Space

- Any logged-in user can create a space.
- A space name must be provided at creation; description, avatar, invite code validity period, etc. are optional.
- The creator automatically becomes the **admin** of the space, and:
  - Cannot remove themselves from the space;
  - Cannot change their own role to editor or viewer.

### 2.2 Joining a Space

There are two ways to join:

1. **Joining Directly via Invite Code**
   - If the space does not have "approval required to join" enabled, a user can join simply by entering a valid invite code.
   - The default role after joining is **viewer**.
2. **Submitting a Join Request (Approval Required)**
   - If the space has "approval required to join" enabled, the user submits a join request after entering the invite code.
   - When the space admin approves the request, they may specify a role (admin/editor/viewer); if not specified, the role entered at the time of the request is used, or viewer by default.
   - If the request is rejected, the user is not a member and cannot access the space or its shared knowledge bases.

### 2.3 Member Count Limit

- A space can set a **member count limit** (default 200; setting it to 0 means unlimited).
- When the limit is reached or exceeded:
  - Joining via invite code, admin adding members, and approval of join requests will all be rejected, with a message indicating "this space is full";
  - New join requests cannot be submitted once the space is full.
- When an admin lowers the limit in settings, if the current member count already exceeds the new limit, the change cannot be saved — members must be removed first, or a higher limit must be set.

### 2.4 Invite Codes

- Only a space **admin** can generate or refresh invite codes.
- An invite code can have a validity period set (e.g., 1 day, 7 days, 30 days, or never expire); once expired, it must be regenerated before it can be used.
- A space has only one valid invite code at any given time; regenerating it invalidates the old one.

### 2.5 Leaving a Space

- A member can leave a space voluntarily (no admin approval required).
- An admin can remove other members (but cannot remove the space creator).
- After leaving or being removed, the user no longer holds any role within that space, and can no longer access its shared knowledge bases through that space.

### 2.6 Deleting a Space

- Only the space **creator** can delete the space.
- Deleting a space releases the sharing relationships for all knowledge bases under that space; members will no longer be able to access those knowledge bases through that space.

## 3. Roles and Permissions Within a Space

There are three roles within a shared space, ranked from highest to lowest permission: **Admin > Editor > Viewer**.

### 3.1 Role Definitions

| Role | English Identifier | Description |
|------|----------|------|
| Admin | admin | Full management of space settings, members, invite codes, and knowledge base sharing |
| Editor | editor | Can edit the content of knowledge bases shared within the space, and can share their own knowledge bases to the space; cannot manage space settings or members |
| Viewer | viewer | Can only view and search knowledge bases shared within the space; cannot share knowledge bases to the space, and cannot manage the space |

### 3.2 Permission Matrix (Capabilities Within the Space)

| Capability | Admin | Editor | Viewer |
|------|--------|--------|------|
| View and search knowledge bases shared within the space | ✓ | ✓ | ✓ |
| Edit the content of knowledge bases shared within the space | ✓ | ✓ | ✗ |
| **Share a knowledge base to this space** | ✓ | ✓ | ✗ |
| Manage knowledge base sharing within the space (unshare, modify sharing permissions, etc.) | ✓ (see below) | Only for sharing they initiated | ✗ |
| Manage space settings (name, description, avatar, invite code validity period, whether approval is required, etc.) | ✓ | ✗ | ✗ |
| Manage members (invite, remove, change roles) | ✓ | ✗ | ✗ |
| Generate/refresh invite codes | ✓ | ✗ | ✗ |
| Approve join requests, permission upgrade requests | ✓ | ✗ | ✗ |
| Submit a permission upgrade request | — | ✓ | ✓ |
| Leave the space | ✓ | ✓ | ✓ |

Notes:

- **"Share a knowledge base to this space"**: only **admins** and **editors** may do this; viewer members cannot share their own knowledge bases to the space.
- **Managing knowledge base sharing within the space**:
  - The initiator of a sharing action can cancel their own sharing, or modify the permission of that sharing record;
  - A space **admin** can cancel any sharing record pointing to this space (e.g., for content governance, or when the initiator has left, etc.).

## 4. Knowledge Base Sharing Rules

### 4.1 Who Can Initiate Sharing

- Only **users within the space that owns the knowledge base** (i.e., users under the account that "owns" the knowledge base) can share that knowledge base to a shared space.
- At the same time, that user must be a **member** of the target shared space, with the role of **admin** or **editor**.  
  That is: **viewer members cannot share any knowledge base (including their own) to the space.**

### 4.2 Setting Permissions When Sharing

When sharing a knowledge base to a space, a **sharing permission** must be specified for "that space":

- **Read-only (viewer)**: space members can, at most, read the knowledge base (the actual effective permission is also constrained by the member's role within the space — see below).
- **Writable (editor)**: space members can be granted editing capability on the knowledge base (also constrained by the member's role).

The same knowledge base can be shared to multiple shared spaces, and each space can be configured with a different sharing permission (e.g., read-only in Space A, writable in Space B).

### 4.3 Updating and Canceling Sharing

- **Modifying the permission of a sharing record**: only **the user who initiated that sharing** can modify it (read-only ↔ writable).
- **Canceling a sharing record**:
  - **The user who initiated that sharing** can cancel it at any time;
  - The **admin** of the target space can also cancel any sharing record under that space (including ones initiated by others).

### 4.4 Sharing the Same Knowledge Base to Multiple Spaces

- Sharing the same knowledge base to multiple shared spaces is allowed.
- Each space has its own sharing record, independently configured with its own permission (read-only/writable).
- For example: knowledge base K is shared to Space A (read-only) and Space B (writable), independently of each other.

## 5. Agent Sharing Rules

Agents can also be shared among members via a shared space, for members to select and use in scenarios such as conversations. The rules are similar to knowledge base sharing, but permissions only support read-only.

### 5.1 Who Can Initiate Agent Sharing

- Only **users within the space that owns the agent** can share that agent to a shared space.
- At the same time, that user must be a **member** of the target shared space, with the role of **admin** or **editor** (consistent with knowledge base sharing).
- The agent must be fully configured (e.g., a model selected, and if it uses a knowledge base, a rerank model selected) before it can be shared.

### 5.2 Permissions When Sharing

- When an agent is shared to a space, only **read-only** is supported: space members can only "use" the agent (e.g., select it in a conversation), and cannot edit the agent's configuration or perform any management action beyond canceling the sharing relationship.
- The same agent can be shared to multiple shared spaces.

### 5.3 Updating and Canceling Sharing

- **Canceling an agent sharing record**:
  - **The user who initiated that sharing** can cancel it at any time;
  - The **admin** of the target space can also cancel any agent sharing record under that space (including ones initiated by others).

## 6. Agent Deactivation Mechanism

"Deactivation" is a personal preference setting that the current space applies to **agents obtained through a shared space**. It only affects how the agent is displayed and used **when selecting an agent in a conversation** within this space, and does not change the sharing relationship or affect other members.

### 6.1 Meaning of Deactivation

- When a space marks an "agent obtained through a shared space" as **deactivated**:
  - In that space's conversation interface, the agent may be hidden from the dropdown list or marked as deactivated, reducing clutter;
  - The agent remains visible and usable to other members of that shared space;
  - The sharing relationship remains unchanged; the user who initiated the sharing and the space admin can still manage that sharing record as usual.
- Deactivation status is recorded by "space + agent (including source space)," meaning: when the same agent is shared by multiple spaces, once a user deactivates it, the display preference for that agent remains consistent across all entry points.

### 6.2 Deactivation and Restoration

- A user can **restore** a deactivated shared agent at any time; once restored, the agent is displayed normally again in lists such as the conversation dropdown.
- Deactivation/restoration only affects the current space's own view and selection list — it does not affect other users, nor does it affect that user's ability to access the agent via other means such as a direct link.
